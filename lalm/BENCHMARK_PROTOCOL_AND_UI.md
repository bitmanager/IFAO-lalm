`Show Charts` включает штатные графики; `Different` показывает различающиеся оценки, `Failures` — непрошедшие проверки. Лупа открывает полный ответ и причины judge. В `Table Settings` можно уменьшить масштаб колонок и скрыть latency: сохранённый providerOutput имеет практически нулевую задержку и не измеряет скорость native inference. Через Columns можно скрыть вспомогательную ветку Gemini, чтобы остальные помещались рядом.

Средний штатный график named metrics нормирует столбцы относительно максимума: это относительное сравнение, не абсолютная accuracy. Точные проценты и знаменатели показаны в заголовках таблицы; левый Pass Rate — исходная доля прохождения всех критериев.

Это готовый promptfoo 0.124.1, не собственный frontend. Перенос результатов — только адаптер формата `export_benchmark_view.py`. Ответы и оценки не перегенерированы. Контейнер не получает API-ключи, модели или GPU; его БД отделена от оригинальных прогонов. Перезапуск сервера не удаляет данные.

Сохранённые отчёты помечены `SAVED REPORT`. **Edit and re-run не запускает новый checkpoint:** в импорт добавлена явная блокирующая assertion. Новый прогон выполняется рецептом ниже, затем импортируется. Ручные оценки в viewer относятся к копии для просмотра, не изменяют первичные результаты и не становятся human gold автоматически.

## Как читать метрики

Два уровня не смешиваются:

1. **ASR629:** Gemini-текст против распознанного текста. WER/CER и смысловые критерии. Это не частота реальных срывов звонков.
2. **Answers204:** пригодность ответа одной Qwen при разных входах. WAV ≤30 секунд, без истории; эта выборка не доказывает преимущество памяти.

Внутри каждого критерия есть три состояния: pass, fail, `UNCERTAIN_REFERENCE` (нужна проверка). Старые grades остаются неизменными; v2 меняет представление, не рубрику:

| Поле в viewer | Значение |
|---|---|
| Исходное имя, например `task_success` | Pass / все примеры; консервативная доля, неопределённость пока тоже не pass |
| `task_success_judged` | Pass / (pass + fail), только там, где judge смог оценить |
| `task_success_coverage` | (pass + fail) / все примеры |
| Красный FAIL с `UNCERTAIN_REFERENCE` | Историческая бинарная отметка; это не доказанная ошибка модели |

Нельзя выбирать более красивое `_judged`, игнорируя coverage. Например, для ответов audio 146/170 против Giga 156/182 — разные знаменатели. На общей пригодной паре audio имеет **10 побед, 14 поражений, 139 равенств; 41 случай требует review**. Для grounding: 14/19/159, 12 review.

Corpus normalized WER остаётся: онлайн 21,31%, Giga 17,83%, Qwen 33,01%. Его не помещаем в pass-график: усреднение покейсных WER дало бы другую метрику. Полные WER/CER и ограничения — в [отчёте](FULL_BENCH_KL1532_20261013.md).

Название старой категории `automated_or_voicemail_excluded` сохранено в provenance, но эти записи фактически входят в 204. Для содержательных ответов смотрим отдельные срезы; общую цифру нельзя считать качеством сложного диалога.

## Проверили самого судью

20 фиксированных записей × 3 системы × 2 критерия × 2 новых повтора: 240 проверок, 0 технических ошибок. Rubric не менялась, кэш отключён.

| Выборка | Совпадение pass/fail | Совпадение pass/fail/review |
|---|---:|---:|
| 12 случайных записей, seed12 | 97,22% | 95,83% |
| 8 заранее проблемных | 77,08% | 66,67% |

20 из 120 критериев хотя бы раз изменили статус между исходной оценкой и двумя повторами. Это повторяемость, **не точность**. Целевая проблемная выборка не репрезентативна всему корпусу. Голосованием результаты не исправляли.

Подготовлена очередь **109 уникальных заданий**: неопределённость, противоречия критериев, нестабильность плюс 30 случайных ID seed42. Причины пересекаются. В ней есть ссылки Label Studio и все исходные тексты. Это очередь будущей разметки, не готовый gold.

Следующий порог доверия — независимая ручная проверка аудио и спорных решений. Случайную часть считать отдельно от целевой; для реальной калибровки — два разметчика и разрешение разногласий. Метрики human agreement/precision критических ошибок пока не заявляем. До этого judge не является автоматическим разрешением релиза.

## Повторить на следующем checkpoint

1. Скопировать фиксированный manifest в новый run directory. Менять только checkpoint path/SHA и явно разрешённую свободную GPU. Аудио, их SHA, история, system prompt, decoding и набор ID должны совпасть.
2. Выполнить готовый native runner: для response — `benchmark_next_reply.py`, для ASR — текущий `benchmark_qwen_calls.py` в режиме v3. Дождаться всех ID; пустые/обрезанные ответы сохранять, не отбирать только успешные.
3. Вычислить WER/CER тем же jiwer и normalization; для response использовать `export_response_promptfoo.py`, для смысловой оценки — `export_asr_semantic_promptfoo.py`.
4. Штатным promptfoo оценить outputs. Любая смена корпуса, rubric, истории или baseline-рецепта — отдельная версия, а не сравнение checkpoint один к одному. Gemini reference и baseline outputs фиксировать; исправленные refs требуют новой версии.
5. Проверить число case IDs, отсутствие технических ошибок и неизменность rubric; конвертировать готовый экспорт и импортировать **как новый eval**, затем использовать штатный Compare.

Пример после готового native response inference на exp:

```bash
python3 lalm/export_response_promptfoo.py "$RUN/manifest.json" "$RUN/results.json" "$RUN/prepared.json"
/mnt/local/drive2/checkpoint-response-bench-v1/tools/run-promptfoo eval \
  -c "$RUN/prepared.json" --no-cache --no-share --max-concurrency 10 \
  --output "$RUN/judge.json" --output "$RUN/judge.html"
# Exit 100 означает провал критериев; отдельно проверить stats.errors == 0.
python3 lalm/export_benchmark_view.py "$RUN/judge.json" \
  --output "$RUN/view.json" --description "RU Answers · checkpoint SHA · fixed cohort" \
  --expected-cases 204
```

Готовый `view.json` помещается в mounted `ui-imports`; затем:

```bash
docker exec asr-bench-view /opt/node/bin/node \
  /opt/node_modules/promptfoo/dist/src/entrypoint.js import /imports/NEW-RUN.json --new-id
```

Нельзя использовать cached ответы предыдущего checkpoint. Public alias GPT-6 Luna не является закреплённой датированной версией: сохраняем дату и repeatability audit, при смене backend перепроверяем контрольную выборку. В текущем сравнении два рецепта Giga (chunked WER и whole-WAV response) различаются; сравнение новых прогонов должно сохранять конкретный recipe внутри каждого трека.

Compose-конфигурация: [benchmark-ui/compose.yaml](benchmark-ui/compose.yaml). Не запускать второй экземпляр на том же порту/имени.

Основной маршрут на exp: `tailscale serve --bg --http=15500 http://127.0.0.1:15500`, tailnet-only. Существующий маршрут 19001 сохранён. Проверено чтение четырёх eval через корпоративную tailnet.

Резервный маршрут на minipc: user unit `asr-bench-view-tunnel.service`, SSH forwarding localhost15500→exp15500, Restart=always. Tailscale Serve HTTPS8445→localhost15500, tailnet-only; маршруты 443/8443/8444 не менялись. Вся БД, результаты и viewer находятся на exp. Прод/test инфраструктуру не меняли.

Корень данных: `/mnt/local/drive2/checkpoint-response-bench-full-v1/`:

- `ui-imports/*-final.json`, `*.summary.json`: полные таблицы, отдельные pass/fail/review, парные сравнения и срезы;
- `ui-state/`: штатная viewer DB; исходная DB отдельно в tools/state;
- `reliability-audit-v1/`: config, provenance, исходные и повторные решения, REPORT.md;
- `human-review-v1/`: queue.json и инструкция, 109 заданий;
- `semantic/`, `native/`, `wer/`: неизменённые исходные артефакты.

Новый adapter проверен сравнением всех 2703 полных ячеек: output, grade, success и исходные named scores совпадают с исходниками. Неполная матрица/дубликаты/технические ошибки приводят к отказу экспорта. Browser-проверка выполнена через реальный HTTPS адрес, таблицы и графики — штатные.

## На что опираемся

- [Promptfoo web UI](https://www.promptfoo.dev/docs/usage/web-ui/): готовые сравнение прогонов, фильтры, графики и ручные отметки. Свой фронтенд не нужен.
- [WER is Unaware](https://github.com/Ufonia/wer-is-unaware): semantic impact и проверка judge на независимых человеческих оценках. Их английскую медицинскую рубрику не переносим напрямую на русские звонки.
- [MT-Bench](https://arxiv.org/abs/2306.05685) и [исследование position bias](https://arxiv.org/abs/2406.07791): судья подвержен смещениям; повторяемость не равна валидности. При будущем pairwise judging надо проверять A/B и B/A.
- [Audio MultiChallenge](https://arxiv.org/html/2512.14865v1#S3): одинаковая фиксированная история и оценка последнего ответа. Для memory-среза нужны audio/text × with/without same history, без будущих реплик; текущий204 этого не заменяет.

Решение: оставить готовый framework, отдельно показывать неопределённость, проверять стабильность judge и накапливать человеческий gold. Дополнительная сложная метрика сама по себе не исправит ненадёжный референс.
